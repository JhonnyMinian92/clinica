# Auditoria del sistema Clinica — 2026-09-11

## Alcance

Auditoria estatica del repositorio completo accesible en `main`, con foco en:

- errores funcionales y regresiones recientes;
- autorizacion, sesiones y CSRF;
- consultas SQL y concurrencia de reservas;
- historial de pacientes y reportes;
- notificaciones email/WhatsApp;
- rendimiento en hosting compartido;
- despliegue en InfinityFree free hosting;
- exposicion accidental de archivos internos;
- estructura de inicializacion de la base de datos;
- HTML/CSS/JS y riesgos de XSS visibles por inspeccion estatica.

## Decisiones del demo

El usuario solicita conservar las credenciales actuales del demo. No se eliminan ni sustituyen en esta auditoria. Esta decision **no debe trasladarse al despliegue real**.

El envio de email y WhatsApp queda preparado por codigo, pero no se activa mientras no exista configuracion real del proveedor.

## Hallazgos y estado

| Severidad | Area | Hallazgo | Estado |

| Alta | Pacientes | Historial de paciente debe respetar el alcance del doctor y no permitir acceso a citas de otros doctores. La implementacion actual usa el identificador de sesion del doctor, que ya se mapea a `doctor_id`. | **Verificado** |
| Alta | Reportes | El alcance de reportes para DOCTOR debe quedar limitado a su `doctor_id`. | **Verificado y reforzado** |
| Alta | Exportacion | CSV podia transportar valores que una hoja de calculo interpretara como formulas. | **Corregido** |
| Alta | Notificaciones | Las llamadas a SMTP/WhatsApp podian producir latencia y repeticion de intentos. | **Corregido** |
| Media | Recordatorios | El sweep aplicaba `TIMESTAMP(date,time)` y podia forzar mas trabajo SQL del necesario. | **Corregido** |

## Reservas

La reserva conserva las medidas importantes ya presentes:

- PDO con consultas preparadas;
- validacion de doctor/especialidad;
- validacion de fecha y hora;
- validacion de documento, email y telefono;
- comprobacion de horario del doctor;
- limite diario por paciente;
- separacion minima entre citas;
- `GET_LOCK()` por doctor para serializar reservas concurrentes;
- restriccion unica `(doctor_id, date, time)` como ultima barrera contra doble reserva;
- transaccion para las operaciones de la reserva.

## Historial de pacientes

El historial usa `patients.id` como vinculo estable y la cedula como identificador funcional para evitar perder continuidad cuando cambia nombre, correo o telefono.

Los doctores estan limitados a sus propias citas; administracion y secretaria conservan el acceso global definido por el sistema.

## Reportes

Los reportes requieren sesion autenticada. Los doctores quedan limitados a sus propios registros. Los reportes de administracion/secretaria pueden filtrar por doctor.

Las exportaciones CSV ahora neutralizan valores que comienzan con `=`, `+`, `-` o `@` para evitar formula injection en hojas de calculo.

## Notificaciones

El flujo queda preparado para:

- confirmacion de cita;
- recordatorio;
- reenvio manual;
- email SMTP;
- WhatsApp mock/Twilio/Meta;
- registro de estado en `notification_log`.

Mejoras aplicadas:

1. Un SMTP no configurado no se intenta conectar durante cada reserva.
2. Los recordatorios no repiten indefinidamente un intento fallido: existe una ventana de enfriamiento de 10 minutos.
3. Un recordatorio enviado queda idempotente por canal/tipo.
4. El sweep usa un lock MySQL no bloqueante.
5. La busqueda de citas del sweep evita aplicar `TIMESTAMP()` a cada fila y conserva un predicado sobre fecha/hora.

## InfinityFree

El proyecto es compatible con el modelo de hosting compartido porque no requiere Composer, framework PHP ni proceso residente.

La version actual de free hosting usa PHP 8.3. El proyecto debe desplegarse respetando el `htdocs` del sitio y usando el host MySQL indicado por la cuenta.

No se debe depender de cron en el free hosting. La logica de recordatorios queda preparada para cron en el hosting de pago y mantiene un mecanismo best-effort desde el dashboard para el demo.

## Inicializacion de BD

`api/seed.php` crea las tablas, aplica las migraciones necesarias e inserta los datos iniciales cuando las tablas estan vacias. No elimina datos existentes.

Para el demo se recomienda:

1. desplegar el codigo;
2. comprobar/configurar las credenciales de `api/db.php` o la configuracion local ignorada;
3. ejecutar `api/seed.php` una sola vez;
4. verificar login, reservas, dashboard e historial;
5. eliminar o renombrar `api/seed.php` despues de inicializar si el sitio queda accesible publicamente.

## Archivos internos

El `.htaccess` agregado bloquea acceso web directo a:

- `.env`;
- `.gitignore`;
- `context.md`;
- `pendiente.md`;
- configuracion local de BD;
- `api/storage`;
- `database`.

Esto no impide que PHP use los archivos internamente.

## Validacion visual

La inspeccion estatica de HTML/CSS/JS no sustituye una prueba visual en un navegador sobre el dominio final. El sistema ya usa rutas base y cache-busting para reducir problemas al desplegar en raiz o subdirectorio, pero la validacion final debe comprobar:

- desktop 1366/1440/1920 px;
- tablet;
- movil;
- menu responsive;
- modal de historial;
- tablas de reportes;
- formulario de reserva;
- login y dashboard;
- mensajes de error y estados vacios.

## Resultado

El repositorio queda **preparado para la fase de despliegue demo en InfinityFree**, con las limitaciones de plataforma documentadas. Las areas de notificaciones quedan preparadas para el posterior hosting de pago sin exigir cambios estructurales en la aplicacion.
